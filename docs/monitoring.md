# Monitoring

| File | Role |
| --- | --- |
| `infra/k8s/monitoring/kube-prometheus-stack.values.yaml` | Helm values for Prometheus, Grafana, node-exporter and kube-state-metrics in the cluster |
| `infra/k8s/monitoring/docker-compose.yml` | Offline viewer on the laptop over the archived metrics |
| `infra/k8s/k8s.mk` | `monitoring_*` targets |

## 1. Design

Prometheus and Grafana run inside each cluster (minikube, staging, production) from the
`kube-prometheus-stack` chart. Clusters are destroyed between uses, so before each destroy a TSDB
snapshot is copied into an archive on the laptop, and a local Prometheus + Grafana reads that
archive. History therefore outlives the clusters at no AWS cost.

| Alternative | Why not now |
| --- | --- |
| Amazon Managed Prometheus + managed scraper + Managed Grafana | Fixed collector fee. |
| In-cluster Prometheus with `remote_write` to Amazon Managed Prometheus | Keeps history in AWS instead of on the laptop.  |
| Grafana Cloud free tier | 14-day retention, no bulk export, metrics stored by a third party |

## 2. Application metrics

Both apps use `prometheus-net.AspNetCore`. `AddMetricServer` starts a second Kestrel listener on
`METRICS_PORT`, which the base Deployments set to `9464` and name `metrics`.  

prometheus-net exports the .NET `System.Diagnostics.Metrics` meters, so the ASP.NET Core
instruments come through without custom code, for example:

| Metric | Labels |
| --- | --- |
| `microsoft_aspnetcore_hosting_http_server_request_duration_*` | `http_route`, `http_request_method`, `http_response_status_code` |
| `microsoft_aspnetcore_server_kestrel_kestrel_active_connections` | `server_port` |
| `system_runtime_dotnet_gc_*`, `process_*` | |

The OpenTelemetry Prometheus exporter would emit the OpenTelemetry names that community Grafana
dashboards expect, but it is still prerelease (`1.20.1-beta.1`).

## 3. Install

Every target runs against the current kubectl context.

```bash
make monitoring_install        
make monitoring_grafana       # prints the admin password, Grafana on http://localhost:3000
make monitoring_uninstall
```

What the values change from the chart defaults:

| Setting | Reason |
| --- | --- |
| Control plane, etcd and kube-proxy scrapes off | Unreachable on EKS, they would show as targets down |
| Alertmanager off | No receiver to send alerts to |
| `enableAdminAPI: true` | Required by the snapshot endpoint. It also exposes series deletion to anything that can reach the Prometheus Service in the cluster |
| Prometheus image tag `v3.15.0` | The chart's default `-distroless` image has no `tar`, which `kubectl cp` needs |
| `retention: 7d`, `retentionSize: 2GB` | Data sits on `emptyDir` (the cluster has no EBS CSI driver); the cap keeps it off the node's disk limit |
| PodMonitor `gaku` | Scrapes port `metrics` of the `gaku-api` and `gaku-web` pods |

Grafana's admin password is generated by the chart and kept in the `monitoring-grafana` Secret.
Grafana and Prometheus are `ClusterIP` only; reach them by port-forward.

## 4. Archive and view

```bash
make monitoring_archive ENV=staging   # before make tf_env_destroy ENV=staging
make monitoring_view ENV=staging       # Prometheus on :9091, Grafana on :3001, Ctrl+C to stop
make monitoring_view_down              # remove the stopped viewer containers
```

`monitoring_archive` asks Prometheus for a snapshot, copies it into
`~/gaku-metrics/<env>` (`local` without `ENV`), and deletes the copy inside the pod. Each run adds
TSDB blocks to the same directory; Prometheus merges blocks that overlap in time, logging
`Overlapping blocks found` at `WARN`, so archiving the same cluster twice is harmless. Environments stay in separate directories because the series
carry no cluster label and would collide.

`monitoring_view` starts Prometheus over that directory with no scrape jobs and a 100-year
retention, so it neither writes new data nor deletes old blocks, and Grafana with that Prometheus
as its data source and anonymous admin access, both bound to `127.0.0.1`. The ports are one above
the cluster port-forwards (`9090`, `3000`), so the viewer runs alongside a live cluster.

## 5. Limits

| Limit | Consequence | Upgrade path |
| --- | --- | --- |
| A destroy without archiving first | That run's metrics are gone | Archiving is step one of [Infrastructure - AWS §10.2 Destroy per env](infra-aws.md#102-destroy-per-env) |
| `emptyDir` storage | A Prometheus pod restart drops everything since the last `monitoring_archive` | EBS CSI driver add-on and `storageSpec` in the values |
| History only on the laptop | Not reachable from elsewhere, not backed up | `remote_write` to Amazon Managed Prometheus with a Pod Identity role |
| No Gaku dashboards | App metrics are queried in Explore; the chart's Kubernetes dashboards exist in the cluster's Grafana only | Dashboard JSON under `infra/k8s/monitoring/`, provisioned in both Grafanas |
| prometheus-net's histogram buckets start at 10ms and double to 167772s (27 per route) | Requests under 10ms share one bucket, so p95 cannot tell 1ms from 9ms | `Metrics.ConfigureMeterAdapter` with `ResolveHistogramBuckets` set to ASP.NET's 5ms–10s buckets |
| Production nodes are `t3.medium` (17 pods each) | Prometheus' 512Mi request and one node-exporter per node may make the autoscaler add a node | Check `kubectl top nodes` after install |
